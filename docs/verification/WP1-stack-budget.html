The ≤48 byte target, read honestly

-fstack-usage reports 8 bytes for hiram_eval_evidence, which satisfies the ≤48 B requirement as written. But GCC split the function: the 8-byte wrapper performs the NULL checks and reaches the 112-byte body through bl, not a tail call — confirmed by disassembly. The frames nest, so the true worst case for calling hiram_eval_evidence is 120 bytes.

Per-function .su numbers do not compose. The figure that belongs in a stack budget is the call-chain total, and the deepest chain is hiram_audit_hazard_vector → hiram_eval_evidence → .part.0 = 256 + 8 + 112 = 376 bytes.

Verdict: the letter of the benchmark is met at 8 B; the honest worst case is 120 B for that entry point and 376 B for the deepest path. The intent — removing a 1.4 KB single-frame allocation that risked silent overflow in an ISR or FreeRTOS task — is decisively met: 1,568 B → 248 B on the scalar audit path, an 84% reduction, with the 1,304-byte memo moved to statically allocated DTCM.

03

Gaps found and closed

critical

The Phase 2 vector API had zero test coverage

hiram_audit_hazard_vector — 84 lines of safety-critical C, the largest stack consumer in the kernel, and the only path to the icing and structural hazards — was referenced by no test, suite, or harness. It shipped entirely unverified. Closed: new tests/test_vector_binding.py, 19 checks: 2,000 randomized differential trials against an independent Python oracle, an exhaustive 729-configuration sweep of the six hazard-driver variables, 400 cross-API consistency states, 8 invalid-input contract cases, and 2 context-lifecycle checks.

critical

A silent cross-module context undersize was possible

hiram_eval.h defaulted CIRCUIT_NODE_COUNT to 81 and sized HiramContext.memo from it, while the generated header defined the authoritative value after including it. Any translation unit allocating a context without the generated header would size it from the stale default while the kernel writes CIRCUIT_NODE_COUNT entries — a silent buffer overflow across a module boundary that no single-file diagnostic can catch. Closed: the generator now emits the dimensions before the include, and the default is replaced by an #error. Verified: allocating a context from hiram_eval.h alone no longer compiles.

high

No link-time proof that the stack cannot reach the context

Removing silent stack overflow is the stated purpose of this work package, yet nothing checked that static DTCM allocation left room for the stack. Closed: _Min_Stack_Size = 0x1000 and a linker ASSERT on _edtcm + _Min_Stack_Size ≤ _estack. Verified by forcing a 128 KB reserve and confirming the link fails with "DTCM exhausted".

high

UBSan was reported as passing while never running

The readiness harness skips the sanitizer unconditionally on Windows (if sys.platform != 'win32') yet still reported instrumented_build: pass. All 2,125,764 exhaustive calls ran with no undefined-behaviour detection while the JSON read as if they had been sanitized. Partly closed: the harness now emits ub_detection_active: false and a reason. The check still cannot run here — this MinGW ships no libubsan.

hardening

Compile-time invariants, reserved-identifier UB, and dead flash

Added four C99 compile-time assertions (context capacity, root index in range, variable count fits the 32-bit mask, hazard id in range) — verified to fire by building against deliberately mismatched headers. Removed the block that #defined __SIZEOF_INT128__, a compiler-reserved identifier (C99 §7.1.3) whose override also silently disabled the 128-bit accumulator it claimed to protect. Marked .dtcm_data as NOLOAD: Reset_Handler never copied it, so 1,304 bytes of initialiser sat in flash and were never transferred — reclaimed, and the section no longer implies an initialisation that does not happen.

On aviation standards

The kernel itself now holds up well: exact rational arithmetic with no floating point, zero heap, no recursion, bounded data-dependent loops, a fixed and provably separated DTCM budget, and a strict-C99 build that survives -Wconversion and -Wcast-qual without a single diagnostic. The engineering is real.

What does not yet hold up is the surrounding evidence. DO-178C DAL-A is a process standard: it wants requirements traced to code and to tests, MC/DC coverage, a plan approved before the work, tool qualification arguments, and configuration management records — reviewed by someone who is not the author. The correct next step is not more tests. It is to retitle the report honestly and write down the gap list, because a self-issued certificate is the one artifact that makes a reviewer distrust everything underneath it.
